# AOS-046 — Real email-link onboarding and ten independent browser sessions

## Goal

AOS-045 verified ten signed Auth JWT identities through real PostgREST, but injected
the two browser test sessions directly into localStorage. AOS-046 removes that
blind spot in the **user onboarding path** and expands actual browser coverage.

## Six connected acceptance workflows

1. **Local email delivery and one-time link:** GoTrue sends a real magic link
   generated by the visible game's login form. The local SMTP sink (Mailpit)
   captures it. The browser follows the *real* GoTrue verification URL, not a
   fabricated token. Its recipient, approved redirect and signed Auth session
   must agree. Credentials and magic URLs must never appear in CI logs.
2. **Host creates a country from the real UI:** After login, the host completes
   the multiplayer creation form. A separate signed API client confirms that
   the country is persisted and owned by precisely that authenticated identity.
3. **Invitation survives the email redirect:** A second distinct person-shaped
   test identity opens `/multiplayer?invite=CODE`, requests its own magic link,
   verifies through GoTrue, retains the original invite query, and uses the
   app's party-join form to claim the second seat. A fresh server read confirms it.
4. **Session continuity and role boundaries:** Each party reloads and remains
   in its own match. The host starts the session using the displayed action;
   the opposition cannot see cabinet-only controls. All data passes the
   actual GoTrue/PostgREST network boundary.
5. **One-time link and signout security:** An already consumed verification
   URL fails to grant a new browser session. Guest signout removes the private
   legislature UI, including after a reload.
6. **Ten browser identities on one legislature:** The prior AOS-045 ten-user
   HTTP fixture now also opens **ten separate Chromium browser contexts**,
   confirms their sessions after reload, ten occupied seats, common national
   history, role-appropriate controls, no horizontal overflow and zero page
   errors. Host and a representative opposition viewport get full axe WCAG
   2.1 A/AA and screenshot checks.

## Boundaries, non-goals and release gates

The test stack is **isolated on localhost** (`http://127.0.0.1:54321`),
with an ephemeral GoTrue server, PostgreSQL and Mailpit. All generated emails
use `example.invalid`; nothing sends an external email. We deliberately never
configure a production mail provider, read a service-role key or contact the
hosted database. We do not mint fake JWTs or bypass the application's normal
email/login UI in the new email test.

Acceptance requires a green `Live Auth acceptance (isolated local stack)` CI
run with explicit `AOS_LIVE_AUTH_PASS` and `AOS_REAL_EMAIL_PASS` receipts,
plus the existing quality CI. On merge, verify the exact release commit's
Vercel deployment status.

**This does not certify** SMTP delivery via a real external provider,
production redirect-URL configuration, ten *human* participant accounts,
editorial weekly publication and fact-checking, or a human visual/keyboard
screen-reader approval. The original 18-gate formal acceptance tally must
not be raised without closing those remaining criteria independently.

Operator walkthrough (future human acceptance):
Use ten separately controlled test accounts, configure the site's permitted
redirects and a production-capable mail provider, complete real email
verification, open the same private invitation, vote and sign on the hosted
site, and record screenshots/receipts without exposing personal credentials
or magic-link tokens.
